### 7.2 スコープ変更プロセス

#### 要求追加の判定基準

新規要求が提案された場合：

```
スコープ追加判定フロー:

1. ビジネス価値評価（1-10点）
   └─ < 7点 → 却下
   └─ ≥ 7点 → 次へ

2. 緊急性評価
   └─ 低 → Won't Haveに分類
   └─ 中〜高 → 次へ

3. MoSCoW再分類
   ├─ Must Have候補 → 既存Must Haveと比較
   │  └─ より低優先度 → Should Haveに格下げ
   │  └─ より高優先度 → 既存要求を格下げしてMust Haveに追加
   ├─ Should Have候補 → Should Haveに追加（スコープ拡大）
   └─ Could/Won't Have → バックログに追加

4. リソース影響評価
   ├─ 追加工数 < 5日 → 承認
   ├─ 追加工数 5-10日 → ステークホルダー承認必要
   └─ 追加工数 > 10日 → 次フェーズに延期またはWon't Have分類

5. 依存関係チェック
   └─ 他要求をブロック → 優先度引き上げ検討
   └─ 独立 → 通常プロセス
```

#### スコープ削減の判定基準

```
スコープ削減判定フロー:

1. トリガー条件
   ├─ 実装工数が見積もりの150%超過
   ├─ クリティカルな技術的障壁発見
   ├─ リソース不足（病欠、緊急対応等）
   └─ ビジネス環境変化

2. 削減候補選定
   ├─ Could Haveから優先的に削減
   ├─ Should Haveの一部延期検討
   └─ Must Haveは原則削減不可（例外: ビジネス判断）

3. ステークホルダー合意
   └─ プロジェクトオーナー承認必須

4. 代替案検討
   ├─ 機能簡素化（MVPバージョン）
   ├─ 次フェーズへ延期
   └─ Won't Haveへ再分類
```

#### 1. **パレートの法則活用**
- 上位20%の要求（Must Haveの一部）で80%の価値創出
- **即実行**: M-1, M-2, M-3, M-9（バンドル最適化、PWA、認証、セキュリティ）

- セキュリティ（M-9）、データ損失（S-9）は即対応

- **コンプライアンスファースト**戦略推奨

- バックエンドAPI統合（S-1）は複雑性高い
- **推奨アプローチ**:
  1. 認証・ユーザー管理API先行実装
  2. 学習進捗API実装
  3. リアルタイム機能統合

- AIコーチング（S-3）は差別化の核心だが技術リスク高い
- **推奨アプローチ**:
  - Phase 1: 基本Q&A機能（プロンプト最適化）
  - Phase 2: 学習プラン提案（ルールベース+AI）
  - Phase 3: 適応型コーチング（完全AI）
- 各Phaseでユーザーフィードバック収集、品質検証

- リソース制約（1名体制）を考慮
- Could Have機能は**条件付き実装**:
  - Phase 1-4成功時のみPhase 5実施
  - ビジネス目標達成済みならスキップ可能
- **おすすめ実装**: C-2（ゲーミフィケーション）、C-7（プッシュ通知）
- **スキップ推奨**: C-1（メンターシップハブ - 複雑度高い）

### 9.2 用語集

- **MoSCoW**: Must have / Should have / Could have / Won't have の優先順位付けフレームワーク
- **タイムボックス**: 固定期間内で達成可能な作業範囲を決定する時間管理手法
- **ROI**: Return on Investment（投資対効果）
- **KPI**: Key Performance Indicator（重要業績評価指標）
- **NPS**: Net Promoter Score（顧客推奨度）
- **MAU**: Monthly Active Users（月間アクティブユーザー）
- **DAU**: Daily Active Users（デイリーアクティブユーザー）
- **GDPR**: General Data Protection Regulation（EU一般データ保護規則）
- **PWA**: Progressive Web App（プログレッシブWebアプリ）
- **IDD**: Issue-Driven Development（Issue駆動開発）

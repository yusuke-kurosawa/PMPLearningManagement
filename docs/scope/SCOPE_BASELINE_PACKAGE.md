## 🎯 エグゼクティブ・サマリー

### プロジェクト概要

PMPLearningManagementプロジェクトは、PMBOK第6版・第7版の学習用包括的PWA対応Webアプリケーションを6ヶ月で開発し、学習時間30%短縮を実現するプロジェクトです。

### 主要目標

1. **バンドルサイズ最適化**: 1.3MB→500KB（62%削減）
2. **PWA完全対応**: オフライン機能実装
3. **API統合完了**: 50+エンドポイント実装
4. **学習効率向上**: 学習時間30%短縮
5. **プロジェクト完了**: 6ヶ月以内（2026-03-28）

### スコープ・ベースライン構成

本ベースラインは以下の3文書で構成され、プロジェクトのすべての作業を定義します：

1. **プロジェクト・スコープ記述書** - v1.0 ✅
2. **WBS（ワーク・ブレークダウン・ストラクチャー）** - v1.0 ✅
3. **WBS辞書** - v1.0 ✅

ベースライン凍結後の変更は、以下のプロセスに従います：

```
変更要求提出
    ↓
変更要求記録（変更管理ログ）
    ↓
影響分析（トリプル制約）
    ├── スコープ影響
    ├── コスト影響
    ├── スケジュール影響
    └── 品質影響
    ↓
変更管理委員会（CCB）評価
    ├── 緊急度・重要度評価
    ├── リスク評価
    └── ROI評価
    ↓
承認/却下/保留の決定
    ↓
承認の場合:
    ├── ベースライン更新（v1.1, v1.2...）
    ├── 関連文書更新
    ├── WBS・スケジュール更新
    └── ステークホルダー通知
    ↓
変更履歴記録
```

#### 変更管理委員会（CCB）構成

| 役割 | 責任 | 意思決定権 |
|------|------|-----------|
| プロジェクトマネージャー | 変更影響分析、推奨事項提示 | 最終承認 |
| テクニカルリード | 技術的影響評価 | 技術的拒否権 |
| ステークホルダー代表 | ビジネス価値評価 | 予算承認 |

#### 変更承認基準

| 変更タイプ | 承認レベル | 承認時間 |
|-----------|-----------|---------|
| **Minor（軽微）** | PM承認のみ | 24時間以内 |
| **Major（重要）** | CCB全員承認 | 1週間以内 |
| **Critical（重大）** | CCB + スポンサー承認 | 2週間以内 |

**Minor変更の例**:
- ワークパッケージ内の作業手順変更
- 成果物のフォーマット変更
- 軽微な受入基準の明確化

**Major変更の例**:
- 新機能の追加
- ワークパッケージの追加/削除
- スケジュール1週間以上の変更
- 予算10%以上の変更

**Critical変更の例**:
- スコープの大幅拡大/縮小
- Phaseの追加/削除
- スケジュール1ヶ月以上の変更
- 予算25%以上の変更

### 4.3 スコープ・クリープ監視

#### 4.3.1 スコープ・クリープ検出

**定義**: ベースラインに含まれない作業が、変更管理プロセスを経ずに追加されること

**監視方法**:
1. 週次進捗会議でWBSとの整合性確認
2. 成果物レビュー時のスコープ妥当性チェック
3. 工数実績とWBS計画の乖離分析

**検出指標**:
- 計画外作業時間の割合（目標: <5%）
- ベースラインにない成果物の出現（目標: ゼロ）
- 要求の非公式追加（目標: ゼロ）

#### 4.3.2 スコープ・クリープ対応

**Level 1（軽微）**: 計画外作業 < 4時間
- 対応: PM判断で許容、次回WBS更新時に反映

**Level 2（中程度）**: 計画外作業 4-16時間
- 対応: 正式な変更要求として処理

**Level 3（重大）**: 計画外作業 > 16時間
- 対応: CCB緊急招集、原因分析、是正措置

### 4.4 パフォーマンス測定（EVM）

#### 4.4.1 EVM基準値

```
PV (Planned Value) = ベースラインWBSの計画工数
EV (Earned Value) = 完了したWPの計画工数
AC (Actual Cost) = 実績工数

SPI = EV / PV （スケジュール効率指数）
CPI = EV / AC （コスト効率指数）

目標:
- SPI ≥ 0.95（スケジュール遅延5%以内）
- CPI ≥ 0.90（コスト超過10%以内）
```

## 📋 8. ベースライン利用ガイドライン

### 8.1 プロジェクト実行時の利用

#### 8.1.1 日常的な参照

**プロジェクトマネージャー**:
- 週次進捗会議前にWBSと実績を照合
- 変更要求時にスコープ記述書で影響範囲確認
- 月次報告書作成時にベースラインとの差異分析

**開発者**:
- 新規タスク着手前にWBS辞書で完了基準確認
- 成果物完成時にスコープ記述書で受入基準確認
- 技術的疑問発生時にWBS辞書で前提条件確認

**ステークホルダー**:
- Phase完了時にスコープ記述書で達成度確認
- 新機能要望時にスコープ外項目リスト確認
- 予算・スケジュール議論時にWBSで妥当性確認

#### 8.1.2 変更要求時の利用

1. **変更要求提出時**:
   - スコープ外項目リストで既存判断確認
   - MoSCoW分類で優先順位妥当性確認

2. **影響分析時**:
   - WBSで影響を受けるワークパッケージ特定
   - WBS辞書で依存関係確認
   - 工数・スケジュール影響試算

3. **承認判断時**:
   - スコープ記述書の目標との整合性確認
   - 制約条件・前提条件への影響確認
   - ベースライン更新の必要性判断

#### 8.1.3 リスク管理時の利用

- WBS辞書の「リスク」欄でワークパッケージ別リスク確認
- スコープ記述書の「制約条件」でプロジェクトリスク確認
- 前提条件の検証でリスク実現の早期検出

### 8.2 ベースライン違反の防止

#### 8.2.1 違反パターンと防止策

| 違反パターン | 防止策 | 責任者 |
|------------|--------|--------|
| **計画外作業の実施** | 週次進捗会議でWBS照合 | PM |
| **スコープ・クリープ** | 変更管理プロセス徹底 | PM |
| **非承認の成果物追加** | 成果物リスト定期確認 | PM |
| **受入基準の非公式変更** | 変更管理ログ記録義務化 | PM |
| **WBS更新の遅延** | ベースライン更新期限設定 | PM |

#### 8.2.2 違反検出メカニズム

1. **自動検出**:
   - 工数入力時のWBSコード必須化
   - WBSにない成果物のアラート

2. **手動検出**:
   - 週次進捗会議での照合
   - 月次EVM分析での計画外工数検出

3. **監査**:
   - Phaseゲートでの包括的レビュー
   - 外部監査（必要時）

### 9.1 ベースライン関連問い合わせ

| 問い合わせ内容 | 連絡先 | 対応時間 |
|--------------|--------|----------|
| **スコープ解釈** | プロジェクトマネージャー | 24時間以内 |

| **ビジネス価値** | ステークホルダー代表 | 1週間以内 |
| **変更要求** | プロジェクトマネージャー | 5営業日以内（CCB） |

### 9.2 エスカレーションパス

```
Level 1: プロジェクトマネージャー（日常的な疑問・軽微な変更）
    ↓（解決しない場合）
Level 2: 変更管理委員会（重要な変更・スコープ解釈）
    ↓（解決しない場合）
Level 3: スポンサー（重大な変更・プロジェクト目標変更）
```

**エスカレーション基準**:
- Level 1→2: 影響工数 > 16h、または判断に迷う場合
- Level 2→3: スコープ大幅変更、予算25%以上変更、スケジュール1ヶ月以上変更
